# USB provisioning and serial/Wi-Fi design discussion

- User wants to remove build-time fixed Wi-Fi credentials/host binding and add USB-assisted pairing/configuration plus serial/Wi-Fi EEG transport. Present the complete proposal at once, consistent with the user's earlier preference against many successive A/B questions.
- User approved the core USB provisioning/serial-Wi-Fi design and then requested campus Wi-Fi support through a PC-created hotspot. Use the existing isolated CP2102N/TLP2361 UART0; explicit Monitor Wi-Fi synchronization reads the current personal-network profile only with consent and OS privileges, with one-time entry fallback. Credentials live in device NVS, never returned in status/logs/recordings or committed to Git; candidate configurations require validation/recovery. NVS persistence must not be described as encrypted without actual encryption support.
- Remove fixed TCP PC IP as well as fixed SSID. USB establishes the paired Monitor identity and a runtime endpoint; discover the paired Monitor on the LAN, with manual endpoint fallback when discovery is blocked. No public/unauthenticated discovery endpoint should automatically receive EEG from every device.
- Dual mode means one EEG output at a time, selected by the user, not simultaneous duplicate streaming. Serial mode can disable Wi-Fi, remains usable offline, and must support the existing control functions without UDP dependency. Wi-Fi mode can still retain USB management.
- Existing payload is 528 bytes per 20 samples at 1000 SPS, about 26.4 kB/s or 264 kbit/s on 8N1. Propose 921600 negotiated after 115200 boot/discovery, with 460800 as a tested fallback; no new PCB/USB-native wiring is required. Actual isolated-link reliability must be measured; component ratings alone do not establish board-level performance.
- Serial needs resynchronizable framing, type/length/CRC, centralized TX ordering, bounded queues and error counters, no unframed ESP_LOG interleaving during a protocol session, and PC four-timestamp synchronization using acquisition time rather than USB receive time. Do not guarantee 1 ms stimulus timing solely from nominal baud rate.
- Decouple management/transport startup from Wi-Fi acquisition of an IP and from ADS bring-up success. Preserve downstream Monitor display, filters, exports, HTTP JSON/device=seu. Mode changes create a new stream_id and an explicit recording segment to avoid hidden discontinuities.
- Consolidated specification: `docs/superpowers/specs/2026-10-11-usb-provisioning-dual-transport-design.md`, approved by the user with explicit authorization to implement. Implementation followed a written module plan because writing-plans was unavailable. Software now includes USB/runtime configuration, serial/Wi-Fi streaming/control, paired discovery and the Windows helper; see `memory/2026-10-13-dual-transport-implementation.md` for delivery/validation boundaries. No hardware, hotspot or firewall changes were made during development.
- Campus scenario: PC authenticates to the campus WLAN; the board joins a separate Windows mobile hotspot using the hotspot credentials, never the campus account password. Monitor receives EEG on the hotspot interface and pushes HTTP on the campus uplink. The board does not require campus/public Internet access; direct enterprise EAP or captive-portal automation is outside this change.
- Shared Wi-Fi helper probes official Windows Tethering capabilities. Supported API control/read is conditional; missing manifest permissions, driver support or policy requires a visible Settings/manual fallback, not disabling firewall or forcing ICS. Expose the hotspot Settings entry, distinguish uplink and hotspot addresses, send the actual hotspot endpoint via USB, do not hardcode 192.168.137.1, do not close the user's hotspot merely on Monitor exit. Optional PC credential persistence uses OS user-protected storage, not plaintext JSON.
- Confirmed via Microsoft primary documentation that Windows can share a Wi-Fi uplink over a mobile hotspot; actual campus policy/routing remains to be tested. Read-only local inspection showed a Wi-Fi Direct adapter and 192.168.137.1, which alone do not prove the hotspot is enabled. No hotspot activation or password retrieval was performed.
